# TS-Orbit — اجرای محلی

**وضعیت انتشار: checkpoint توسعه تا پایان مرحلهٔ ۶، به‌همراه بهینه‌سازی برای میزبانی و بازبینی رابط کاربری (دسته‌های ۱ تا ۳)؛ دستهٔ ۴ بازبینی و مراحل ۷ و ۸ باقی‌اند.** هدف، عرضهٔ محصول عمومی پس از تکمیل و پذیرش نهایی است.

برای شناخت هدف محصول، تمام بررسی‌ها و اصلاحات، شواهد آزمون و نقشهٔ تکمیل و عرضه، [سند جامع پروژه](PROJECT-DOSSIER-FA.md) را بخوانید.

رابط React/TypeScript و سرور Express/Socket.IO برای فضای کاری، پروژه، وظایف، سازمان و گفتگو. ذخیرهٔ پایدار SQLite، هویت و کنترل دسترسی، سرویس‌های کسب‌وکار، فایل واقعی، نسخه‌بندی، پورتال مشتری، چت و اعلان‌های واقعی تا مرحلهٔ ششم پیاده شده‌اند. اتوماسیون، اتصال‌های بیرونی و بهینه‌سازی نهایی طبق مراحل بعدی تکمیل می‌شوند.

## شروع سریع

پیش‌نیاز: [Node.js 24](https://nodejs.org/) (نسخهٔ 24.19 یا جدیدتر از شاخهٔ 24) و npm 10 یا جدیدتر. روی Windows، macOS و Linux کار می‌کند.

```bash
git clone https://github.com/ALiTahmores/TS-Orbit-Local.git
cd TS-Orbit-Local
npm ci
npm run build
npm run local:account -- bootstrap --email you@example.com --name "Your Name" --phone "09120000000"
npm start
```

فرمان `bootstrap` حساب مالک را می‌سازد و رمز را دو بار (بدون نمایش) می‌پرسد؛ فقط یک بار و روی نصب خالی اجرایش کنید. سپس http://127.0.0.1:3000 را باز کنید و با همان ایمیل و رمز وارد شوید. داده‌ها در پوشهٔ `data/` کنار پروژه ذخیره می‌شوند و در گیت نیستند.

- حالت توسعه با بارگذاری خودکار: `npm run dev`
- بررسی نوع‌ها و تست‌ها: `npm run lint` و `npm test`
- تنظیمات اختیاری (پورت، مسیر داده، اجرا پشت دامنه): `.env.example` را به `.env` کپی و ویرایش کنید.

## تغییرات این نسخه

- **سرعت و میزبانی:** بارگذاری تنبل صفحه‌ها و تقسیم bundle، فشرده‌سازی brotli/gzip هنگام build، هدرهای امنیتی (CSP و…) در حالت production، کش طولانی فایل‌های نسخه‌دار، پشتیبانی `TRUST_PROXY` برای اجرا پشت reverse proxy، و صف رمزنگاری که سرور را هنگام ورود هم‌زمان قفل نمی‌کند.
- **رفع خطاهای مهم:** حلقهٔ بی‌پایان ذخیره در نقشهٔ راه، ثبت‌نام بدون ورود خودکار، باز نشدن پنجرهٔ ویرایش وظیفه، جابه‌جایی پنجره‌ها، افزودن عضو، برچسب نقش‌ها و ارسال پیام با Enter.
- **حذف داده‌های ساختگی:** داشبوردها، نمودارها، صفحهٔ تیم، کارکرد اعضا، گزارش‌ها، نشست‌های فعال، تقویم سررسیدها و پورتال فقط دادهٔ واقعی فضای کاری را نشان می‌دهند؛ حذف عضو از فضای کاری واقعی شد؛ پورتال پروژه‌های جدید به‌طور پیش‌فرض بسته است؛ حدود ۶۰ فایل بلااستفاده حذف شد.
- **یکدستی ظاهری:** تاریخ شمسی با یک انتخابگر مشترک در همهٔ فرم‌ها، ارقام لاتین در لینک‌ها و کدها، فرم‌های مرتب برای فایل‌ها و پورتال و چک‌لیست‌ها، حذف برچسب‌های انگلیسی و اصطلاحات فنی، منوی کناری کوتاه‌تر و کانبان بدون ستون بریده.

## پیش‌نیاز و اجرا

Node.js 24.19.0 یا جدیدتر از شاخهٔ 24، npm 10 یا جدیدتر و دیسک محلی لازم است. موتور SQLite هنگام اجرا بررسی می‌شود و حداقل 3.51.3 لازم است؛ نسخهٔ آزموده‌شده 3.53.3 بود. فقط یک پردازش سرور اجرا کنید.

```powershell
npm ci
npm run build
npm run db -- status
```

برای نصب خالی، مالک را با فرمان زیر بسازید؛ سرور باید متوقف باشد:

```powershell
npm run local:account -- bootstrap --email owner@example.test --name "Local Owner" --phone "09120000000"
npm start
```

رمز دو بار، بدون نمایش، گرفته می‌شود: حداقل ۱۲ نویسه و حداکثر ۷۲ بایت UTF-8. آدرس پیش‌فرض http://127.0.0.1:3000 است. ثبت‌نام عمومی USER با workspace شخصی ایجاد می‌کند؛ مالک سیستم جدید ساخته نمی‌شود.

اگر از نسخهٔ قبلی داده دارید، ابتدا دستورهای مهاجرت پایین را اجرا کنید. اگر مالک موجود است، bootstrap را اجرا نکنید؛ رمز همان حساب را بدون تغییر ID/عضویت تنظیم کنید:

```powershell
npm run local:account -- set-password --email YOUR_EXISTING_EMAIL
npm start
```

بازیابی رمز، نشست‌ها را با نگهداری تاریخچه revoked می‌کند و کلید امضای مرجع در SQLite را در همان transaction عوض می‌کند؛ تمام کاربران دوباره وارد می‌شوند. فایل jwt-secret فقط mirror سازگاری است؛ مقدار SQLite مرجع است. بازیابی مرورگری روش محلی را توضیح می‌دهد و ایمیل یا کد ساختگی ندارد.

برای توسعه `npm run dev` و برای نسخهٔ ساخته‌شده `npm start` اجرا کنید. dev مستقل از NODE_ENV ارثی است. `dist/client` عمومی و `dist/server` خصوصی است. `npm run clean` فقط dist را حذف می‌کند؛ داده‌ها حذف نمی‌شوند.

## تنظیمات و مسیر داده

در صورت نیاز `.env.example` را به `.env` کپی کنید. HOST=127.0.0.1، PORT=3000 و DATA_DIR=./data پیش‌فرض‌اند؛ APP_ORIGIN خالی از host/port ساخته می‌شود. داده باید خارج public/dist و ریشه یا والد پروژه باشد. symlink/junction برای مسیر داده مجاز نیست. فایل `DATA_DIR/orbit.sqlite` مرجع است؛ JSON قدیمی فقط مبدا مهاجرت/آرشیو است و دیگر هم‌زمان نوشته نمی‌شود.

قفل تک‌پردازشی در مسیر `DATA_DIR.lock`، بیرون پوشهٔ قابل جابه‌جایی، نگهداری می‌شود. توقف سرور برای تمام ابزارهای نگهداری لازم است. خرابی دیتابیس یا نسخهٔ ساختار نامعتبر startup را متوقف می‌کند؛ reset یا seed خودکار ندارد. از دیتابیس روی network share استفاده نکنید.

## مهاجرت JSON قدیمی

```powershell
npm run db -- dry-run --source "C:\path\to\old-db.json"
npm run db -- import --source "C:\path\to\old-db.json"
npm run db -- status
```

dry-run فقط می‌خواند. import در دیتابیس جدید/خالی انجام می‌شود؛ ورود مجدد همان فایل با SHA یکسان رکورد تکراری ایجاد نمی‌کند. ورود فایل متفاوت به دیتابیس دارای داده رد می‌شود؛ ادغام حدسی انجام نمی‌شود. نسخهٔ موقت پس از import تراکنشی و integrity check به‌صورت انحصاری منتشر می‌شود. اصل فایل، شناسه‌ها، ترتیب رکوردها، فیلدهای اضافی و وضعیت‌های قدیمی حفظ می‌شوند. ردیف‌های ناسازگار حذف نمی‌شوند؛ نسخهٔ اولیه و issueها در آرشیو/quarantine ثبت و ناسازگاری شناخته‌شده برای سازگاری نگهداری می‌شود. ارجاع یا هویت ناسازگار جدید رد می‌شود.

اگر `DATA_DIR/db.json` نسخهٔ قبلی موجود باشد و orbit.sqlite وجود نداشته باشد، نخستین اجرا آن را مهاجرت می‌دهد و JSON را حفظ می‌کند. LEGACY_DB_IMPORT نیز برای مبدا صریح در دیتابیس جدید قابل استفاده است. اگر SQLite موجود باشد، آن مرجع است. رمزهای عمومی قدیمی در راه‌اندازی حساب غیرفعال می‌شوند؛ از set-password استفاده کنید.

داده‌های localStorage مرورگر و blobهای ازبین‌رفته داخل JSON نیستند؛ این ابزار آن‌ها را خودکار حدس یا بازیابی نمی‌کند. تاریخ جلالی/نامفهوم در اصل داده حفظ و بدون UTC ساختگی گزارش می‌شود. وضعیت و واحد مبلغ قدیمی نیز حفظ است؛ تطبیق کامل مدل‌های کسب‌وکار مراحل بعدی است.

## پشتیبان، بازیابی و rollback

سرور را متوقف کنید. مقصد backup باید پوشهٔ جدید و خارج DATA_DIR باشد:

```powershell
npm run db -- backup --output "C:\OrbitBackups\checkpoint-01"
npm run db -- restore --source "C:\OrbitBackups\checkpoint-01"
```

Snapshot سازگار SQLite همراه فایل‌های پایدار داخل DATA_DIR و manifest هش ساخته می‌شود؛ قطعه‌های آپلود ناتمام در `files/staging` داخل پشتیبان نمی‌آیند. تمام نسخه‌های فعال فایل مدیریت‌شده با اندازه و SHA-256 ثبت‌شده در دیتابیس تطبیق داده می‌شوند. محتوای مدیریت‌شدهٔ مفقود یا خراب، ساخت پشتیبان یا بازیابی را متوقف می‌کند؛ رکوردهای قدیمی که از ابتدا فقط metadata یا blob URL ازبین‌رفته داشتند محفوظ و صریحاً غیرقابل دریافت‌اند. پشتیبان شامل اطلاعات خصوصی، credentialها و کلید امضاست؛ جدا از سورس و انتشار نگهداری کنید. restore پیش از تغییر داده، هش همهٔ فایل‌ها، شمارش‌ها، schema، integrity و رابطهٔ نسخه‌ها با محتوا را بررسی می‌کند؛ سپس پوشهٔ قبلی را با نام `.previous-UUID` حفظ می‌کند و نسخهٔ معتبر را جایگزین می‌کند.

اگر عملیات restore قطع شود، marker `DATA_DIR.restore-pending` مانع شروع با دیتابیس خالی می‌شود. برای بازیابی قابل بررسی:

```powershell
npm run db -- recover-restore
```

فرمان، مسیرها و هش‌های ثبت‌شده را بررسی و در حالت روشن، نسخهٔ قبلی یا انتشار کامل را بازیابی/تأیید می‌کند؛ در حالت مبهم، داده‌ها را دست‌نخورده نگه می‌دارد و خطا می‌دهد.

برای برگشت به ذخیرهٔ JSON نسخهٔ قبلی، export را در فایل جدید انجام دهید و با سورس checkpoint مرحلهٔ اول و DATA_DIR جدا استفاده کنید؛ SQLite فعال را با JSON هم‌زمان ننویسید:

```powershell
npm run db -- export --output "C:\OrbitBackups\rollback-db.json"
```

## اعتبارسنجی و محدودیت‌ها

```powershell
npm run lint
npm run build
npm test
```

تست‌ها از داده‌های موقت جدا استفاده می‌کنند. تغییر معتبر قبل از پاسخ HTTP و ارسال رویداد commit می‌شود؛ خطای رابطه 422 و خطای ذخیره 503 می‌دهد و حافظه rollback می‌شود. حذف رکورد دارای وابستگی بدون تغییر سازگار وابستگی‌ها رد می‌شود؛ سیاست‌های cascade در سرویس‌های کسب‌وکار تکمیل می‌شوند.

سرویس‌های کسب‌وکار repository با محدودهٔ دسترسی دارند و تغییر چند رکورد را در transaction موجود انجام می‌دهند. ذخیره‌سازی مرحلهٔ چهارم فقط ردیف‌ها و روابط تغییرکرده را می‌نویسد؛ جدول نامرتبط پاک و دوباره ساخته نمی‌شود. مدل سازگار در حافظه و payloadهای JSON برای حفظ دادهٔ قدیمی باقی است؛ خواندن و اعتبارسنجی هنوز برای همهٔ داده‌ها انجام می‌شود و این نسخه برای یک پردازش محلی طراحی شده است. این checkpoint تحویل نهایی همهٔ قابلیت‌ها نیست.

## هویت و دسترسی مرحلهٔ سوم

نشست JWT هشت‌ساعته به حساب زنده، شناسهٔ نشست و هش شناسهٔ توکن در SQLite وابسته است. خروج، پایان نشست، تغییر رمز یا شناسهٔ ورود و غیرفعال‌کردن حساب، نشست را لغو و Socket مرتبط را قطع می‌کنند. تغییر ایمیل، نام کاربری یا هویت شمارهٔ همراه به رمز فعلی نیاز دارد. پاسخ 401 ورود دوباره می‌خواهد؛ 403 مجوز کافی ندارد و به‌خودی‌خود حساب را خارج نمی‌کند. پس از قطع شبکه، وضعیت ذخیره نامعلوم است؛ با بارگذاری مجدد بررسی کنید.

`systemRole=ADMIN` فقط مدیریت حساب و نشست می‌دهد. OWNER فضای کاری مدیر سیستم نیست؛ مدیر سیستم هم بدون عضویت واقعی، دادهٔ کسب‌وکار فضای دیگر را نمی‌خواند. مرجع عضویت `workspace.ownerId` و اعضای فعال با `userId` است؛ ایمیل یا نسخهٔ عضویت در پروفایل، مجوز ایجاد نمی‌کند. نقش نمایشی حساب با نقش عضو فضای کاری جدا است. `x-workspace-id` فضای فعال را انتخاب می‌کند؛ ناسازگاری آن با query/body رد می‌شود. مسیرهای API به حروف کوچک/بزرگ حساس‌اند.

نخستین اجرای نسخهٔ جدید، مهاجرت هویت را یک بار در transaction ثبت می‌کند؛ مالک سیستمی تاریخی حفظ و نشست قدیمی بدون SID معتبر لغو می‌شود. شناسه‌ها و داده‌های قبلی حذف نمی‌شوند. ردیف قدیمی بدون رابطهٔ معتبر با فضای کاری محفوظ می‌ماند و از API کسب‌وکار نمایش داده نمی‌شود؛ انتساب حدسی انجام نمی‌شود.

دعوت عمومی با کد تصادفی فقط عضویت MEMBER می‌دهد؛ دعوت ایمیلی به ایمیل حساب مقصد و مهلت هفت‌روزه وابسته است. ایمیل واقعاً ارسال نمی‌شود و رابط همین را اعلام می‌کند. جست‌وجوی حساب بیرون فضای کاری فقط برای مدیر فضای کاری و با تطبیق دقیق ایمیل/نام کاربری، با پاسخ محدود هویتی انجام می‌شود.

پورتال عمومی فقط توکن دقیق پورتال فعال را می‌پذیرد؛ شناسهٔ پروژه یا بخشی از توکن پذیرفته نیست. فعال/غیرفعال‌کردن و چرخاندن لینک در سرور ذخیره می‌شود؛ توکن جدید ۳۲ بایت تصادفی است. فایل و وظیفه فقط با visibility صریح و رابطهٔ همان پروژه عرضه می‌شوند. بارگذاری/دانلود واقعی، تاریخچهٔ بازخورد، پاسخ و تأیید در بخش مرحلهٔ پنجم توضیح داده شده‌اند.

کلید اتصال WordPress از مسیر `GET /api/sites/:projectId/key` فقط برای مدیر فضای کاری قابل دریافت است. پیام connector باید کلید همان سایت، `projectId/siteUrl` همان ثبت و `X-WP-Sync-Signature` برابر HMAC-SHA256 از بدنهٔ JSON خام داشته باشد؛ کلید نشست کاربری ایجاد نمی‌کند. اتصال به WordPress واقعی، تولید/اجرای افزونه و جایگزینی آمار شبیه‌سازی‌شده در مرحلهٔ هفتم آزموده می‌شوند.

`npm run test:stage3` آزمون همین مرحله و `npm test` آزمون تمام مراحل تکمیل‌شده را اجرا می‌کند. پیش از آن build لازم است. سورس ZIP شامل داده، کلیدها یا نشست شخصی شما نیست؛ پشتیبان خصوصی را جدا نگه دارید.

Docker Compose اختیاری است و روی loopback منتشر می‌شود؛ Node/SQLite داخل تصویر باید شرط بالا را پاس کنند. Docker/nginx در این checkpoint اجرا و آزموده نشده‌اند. فونت Vazirmatn با OFL و آواتارهای SVG محلی‌اند؛ سرویس‌های اختیاری WordPress/SMS برای عملیات واقعی به اتصال خود نیاز دارند.

## سرویس‌های کسب‌وکار مرحلهٔ چهارم

پروژه، وظیفه، زیرکار، نظر، نقطهٔ عطف و ثبت زمان از سرویس‌های مستقل و repository مشترک استفاده می‌کنند. شناسه، نویسنده، فضای کاری، شمارنده و تاریخچه را سرور تعیین می‌کند. چندمسئول با ID واقعی، وابستگی بدون چرخه، برچسب، برآورد زمان، لینک و پیوستِ فایل موجود ذخیره می‌شوند. مجموع زمان از time entryهای پایدار به دست می‌آید؛ انتقال وظیفه شمارندهٔ هر دو پروژه و روابط فرزند را به‌روز می‌کند.

وضعیت اصلی وظیفه `pending/inprogress/review/completed/blocked/cancelled` و اولویت `low/medium/high/critical` است؛ نام‌های نمایشی قدیمی به این مقادیر تبدیل می‌شوند. تکمیل با وابستگی یا زیرکار باز رد می‌شود. تاریخ میلادی و جلالی عددی معتبر، مقدار canonical جدا دارند؛ متن قدیمی مبهم محفوظ می‌ماند و به تاریخ ساختگی تبدیل نمی‌شود. مبلغ عددی فقط با مقدار و واحد صریح ذخیره می‌شود؛ از متن بودجهٔ قدیمی نرخ یا واحد حدس زده نمی‌شود.

تیم، دپارتمان، نقش اعضا، ماژول، ناوبری و گزارش دادهٔ واقعی دارند. ایجاد تیم، کانال‌ها و یک رویداد سیستمی مربوط به همان ایجاد را ذخیره می‌کند؛ GET یا تغییر اعضا پیام نمونه تولید نمی‌کند. سطرهای ماژول از endpointهای اتمیک `/api/org/module-instances/:id/records` ایجاد، ویرایش و حذف می‌شوند؛ بازنویسی کل `config.records` رد می‌شود. چک‌لیست WordPress/SEO، محتوای در حال بررسی و چرخهٔ رفع/تأیید/بازگشایی باگ نیز CRUD پایدار دارند.

مجوز صریح دپارتمان برای نقش عضو یا تیم واقعی اعمال می‌شود؛ منع دسترسی بر همهٔ والدهای مرتبط اثر دارد. این مجوز هرگز VIEWER را نویسنده نمی‌کند. شمارندهٔ ذخیره‌شده شامل همهٔ فرزندان معتبر است، ولی پاسخ هر کاربر فقط دادهٔ مجاز خودش را نشان می‌دهد. رویداد پروژه/وظیفه فقط نیاز به تازه‌سازی را اعلام می‌کند تا محتوای خصوصی از دید کاربر دیگری کپی نشود. گزارش‌های تولیدشده نیز محدودیت مخاطب دپارتمان دارند.

جزئیات گزارش، snapshot ذخیره‌شده هنگام صدور را نمایش می‌دهد؛ آمار زندهٔ فضای کاری جایگزین دادهٔ تاریخی نمی‌شود. پروژهٔ متعلق به دپارتمان حتی پیش از تعریف وظیفه شمرده می‌شود و وظیفهٔ لغوشده، باز یا معوق نیست. سررسید بدون ساعت تا پایان روز تقویمی سیستم میزبان معتبر است؛ سررسید دارای ساعت و منطقهٔ زمانی با همان لحظهٔ دقیق مقایسه می‌شود.

حذف، وابستگی‌های همان دامنه را پاک یا جدا می‌کند. رابطهٔ قدیمی مبهم یا وابستگی به هویت/نشست، حذف را با خطای 409 متوقف می‌کند؛ حساب کاربر برای حذف یک پروژه پاک نمی‌شود. مهاجرت `domain_references_v1` ناسازگاری‌های جدیداً شناخته‌شدهٔ قدیمی را آرشیو می‌کند و ایجاد ناسازگاری تازه را نمی‌پذیرد. پشتیبان قبل از ارتقا همچنان ضروری است.

`npm run test:stage4` آزمون‌های این مرحله و `npm test` همهٔ مراحل تکمیل‌شده را اجرا می‌کند. ابتدا build انجام دهید. پیوستِ وظیفه به ID فایل واقعی متصل است؛ مرحلهٔ پنجم زیرساخت بایت و نسخه را اضافه می‌کند. ابزارهای شبیه‌سازی‌شدهٔ اتوماسیون و اتصال WordPress واقعی در این مرحله نهایی نشده‌اند.

## فایل واقعی و پورتال مرحلهٔ پنجم

آپلود از فایل واقعی مرورگر، محتوا را به‌صورت stream در `DATA_DIR/files/staging` می‌نویسد، اندازه و نوع و امضای اولیهٔ فایل را بررسی می‌کند، SHA-256 می‌گیرد و پیش از commit دیتابیس محتوای syncشده را با نام داخلی تصادفی در `files/blobs` منتشر می‌کند. نام کاربر وارد مسیر ذخیره‌سازی نمی‌شود. در خطای SQL یا قطع درخواست، فایل موقت/منتشرشده rollback می‌شود و رکورد موفقیت ساخته نمی‌شود. دانلود پس از بررسی مجوز، digest و نسخه، transaction را پیش از اولین بایت تمام می‌کند و پاسخ attachment با `nosniff` می‌دهد؛ HEAD و یک byte range پشتیبانی می‌شوند.

حد پیش‌فرض هر فایل ۲۵ MiB است. `FILE_MAX_BYTES` عدد صحیح بین ۱ و ۱۰۷۳۷۴۱۸۲۴ بایت می‌پذیرد. انواع مجاز شامل PDF، سندهای Office/OpenDocument، TXT/MD/CSV/JSON، تصویرهای PNG/JPEG/GIF/WebP/ICO/BMP، ZIP/7z/RAR/GZ، MP3/WAV/OGG/M4A، MP4/MOV/WebM و FIG است. پسوند و MIME باید سازگار باشند؛ باینری‌های شناخته‌شده با امضای اولیه بررسی می‌شوند. فایل اجرایی و محتوای فعال HTML/SVG/PHP پذیرفته نیست. هر نسخهٔ جدید یک رکورد و محتوای تغییرناپذیر مستقل دارد؛ تأیید نسخهٔ قبلی، نسخهٔ تازه را خودکار تأیید نمی‌کند.

فایل پروژه، وظیفه و گفتگو علاوه بر فضای کاری، به تمام والدهای معتبر و مجوزهای دپارتمان و مشارکت در گفتگو محدود است. نویسنده یا مدیر واقعی می‌تواند فایل را تغییر دهد؛ انتشار در پورتال به تأیید مدیر نیاز دارد. حذف، ابتدا tombstone و قصد پاک‌سازی را پایدار می‌کند و بعد از commit بایت‌های مربوط پاک می‌شوند. پاک‌سازی در شروع بعدی نیز تکرار می‌شود و فقط نام‌های داخلی معتبر در پوشهٔ مدیریت‌شده را لمس می‌کند. ارجاع‌ها و تاریخچهٔ حذف برای حسابرسی باقی می‌مانند.

API خصوصی: `POST /api/files` و `POST /api/files/:id/versions` بدنهٔ باینری و سربرگ ASCII `X-File-Metadata=encodeURIComponent(JSON.stringify(metadata))` دارند. metadata فقط `name/projectId/taskId/conversationId/category/tag/clientVisible/approved/note` را می‌پذیرد؛ شناسه، نویسنده و digest را سرور می‌سازد. فهرست، metadata، نسخه‌ها، تغییر مشخصات و حذف زیر `/api/files` هستند؛ دانلود از `/api/files/:id/download` یا `/api/files/:id/versions/:versionId/download` انجام می‌شود. رابط برای دریافت خصوصی از نشست فعلی استفاده می‌کند و URLهای blob فقط برای دریافت موقت ساخته و آزاد می‌شوند.

پروژهٔ تازه و چرخش پیش‌فرض لینک، انقضای ۳۰ روزه دارند؛ مدیر می‌تواند تاریخ دقیق یا `null` برای نبود انقضا ثبت کند. لینک تاریخیِ دقیق بدون فیلد انقضا تا لغو صریح حفظ می‌شود. انقضای نامعتبر یا گذشته، workspace غیرفعال و لینک لغوشده رد می‌شوند. فعال‌سازی پس از لغو، توکن تازه می‌دهد. نسخهٔ فایل فقط در صورت تأیید و visibility صریح از توکن همان پروژه دانلود می‌شود؛ توکن مشتری، JWT خصوصی ارسال نمی‌کند.

مشتری می‌تواند از همان لینک، پیوست واقعیِ تأییدنشده بارگذاری و بازخورد ثبت کند؛ این آپلود به‌تنهایی فایل را برای دانلود عمومی منتشر نمی‌کند. مالک اعلان پایدار می‌گیرد. مدیر وضعیت و پاسخ را ثبت می‌کند و مشتری تاریخچه و پاسخ‌های مجاز را می‌خواند. GET بازخوردهای قدیمی را بدون تغییر می‌خواند؛ نخستین ویرایش مجاز، رکورد تاریخی توکار را به مجموعهٔ مرجع منتقل می‌کند. موفقیت و رویدادها بعد از commit اعلام می‌شوند.

`npm run test:stage5` آزمون‌های فایل، پورتال، خرابی/قطع درخواست، مرز stream، backup/restore و قراردادهای رابط را اجرا می‌کند؛ `npm test` همهٔ مراحل را پوشش می‌دهد. ابتدا `npm run build` لازم است. برای backup/restore سرور را متوقف کنید؛ قفل پردازش از تغییر هم‌زمان داده جلوگیری می‌کند. jobs و اتصال‌های بیرونی در مراحل بعد باقی‌اند.

## چت، حضور و اعلان مرحلهٔ ششم

نمای فعال پیام‌رسان به `server/chat` و SQLite متصل است؛ پیام، مخاطب، ساعت، وضعیت خواندن و صوت نمونه تولید نمی‌کند. گفتگوی مستقیم، گروه عادی، کانال تیم، مدیریت اعضا، درخواست ارتباط بین تیمی، تأیید/رد/مسدودسازی و لغو مجوز از API واقعی استفاده می‌کنند. هویت فرستنده، شناسه، زمان و تاریخچه را سرور تعیین می‌کند. GET داده را تغییر نمی‌دهد.

عضویت فعال فضای کاری و گفتگو در HTTP، آپلود/دانلود و هر رویداد Socket دوباره بررسی می‌شود. گروه عادی به مجوز ارتباط جاری اعضا وابسته است؛ لغو مجوز بین تیمی از طریق گروه دور زده نمی‌شود. گروهی که مدیر واقعی فضای کاری صریحاً ساخته یا عضو آن را دعوت کرده است مجوز گروه مستقل دارد؛ حذف عضویت، آن دسترسی را لغو می‌کند. مدیر فضای کاری بدون عضویت در گفتگوی خصوصی، محتوای آن را نمی‌خواند. VIEWER پیام نمی‌فرستد، ولی رسید خواندن و ترجیح بی‌صداکردن خودش را ثبت می‌کند.

پیام متنی، قطعه کد، پاسخ، ویرایش، حذف با tombstone و تاریخچه، واکنش، سنجاق، بایگانی/بازگشایی و بی‌صداکردن ذخیره می‌شوند. رسید خواندن برای هر کاربر مستقل و رو به جلو است؛ دریافت پیام قدیمی، cursor را عقب نمی‌برد. پیام‌های قدیمی‌تر با صفحه‌بندی قابل دریافت‌اند. آرشیو مانع ارسال جدید است و تاریخچه را پاک نمی‌کند.

برای فایل و صوت ابتدا فایل واقعی با `conversationId` از سرویس مرحلهٔ پنجم بارگذاری می‌شود؛ سپس ID آن با `attachmentIds` به پیام متصل می‌شود. نسخهٔ همان زمان داخل پیام ثبت می‌شود؛ جایگزینی فایل، بایت پیوست پیام قبلی را عوض نمی‌کند. فایل سایر گفتگوها و محتوای ساختگی پذیرفته نیست. صوت از MediaRecorder واقعی مرورگر می‌آید؛ نبود مجوز یا میکروفن خطای روشن می‌دهد و صوت جایگزین ساخته نمی‌شود. WebM صوتی با MIME `audio/webm` نگهداری می‌شود. پخش و پیش‌نمایش از دریافت احرازشدهٔ نسخهٔ ثابت استفاده می‌کنند و URL موقت آزاد می‌شود. محدودیت نوع و اندازهٔ سرویس فایل همچنان برقرار است.

اتصال Socket.IO به token نشست و فضای کاری جاری وابسته است. join، leave، typing و seen شناسهٔ هویت ارسالی را جایگزین هویت تأییدشده نمی‌کنند. تأیید seen پس از commit است؛ خطای SQL موفقیت یا رویداد جعلی ندارد. نشست منقضی/لغوشده و عضویت نامعتبر اتصال را قطع می‌کنند. reconnect اطلاعات مجاز را دوباره می‌خواند و گفتگوی فعال را دوباره join می‌کند؛ logout و تغییر حساب/فضا، اتصال و cache قبلی را کنار می‌گذارند. پاسخ دیررس گفتگوی قبلی، پیام یا پیش‌نویس گفتگوی جدید را جایگزین نمی‌کند.

حضور آنلاین از اتصال‌های زندهٔ معتبر محاسبه می‌شود؛ `status` حساب و مجوزهای تأیید/مسدودسازی در دیتابیس با وصل یا قطع Socket تغییر نمی‌کنند. در فهرست همکاران، `status` و `presenceStatus` برای نمایش حضورند و `accountStatus` جداست. اعلان‌های رویداد Socket صرفاً نیاز به تازه‌سازی را اعلام می‌کنند؛ رابط projection مجاز خودش را می‌خواند.

`server/notifications` اعلان شخصی، خواندن تکی/همه و پاک‌سازی شخصی را ذخیره می‌کند. پاک‌سازی با `dismissedAt` است و وضعیت شخص دیگر تغییر نمی‌کند. پیام و درخواست چت، واگذاری جدید وظیفه و بازخورد مشتری اعلان واقعی تولید می‌کنند؛ ویرایش نام وظیفه اعلان واگذاری تکراری نمی‌سازد. فعالیت از رویداد سرور و هدف واقعی ساخته و هنگام خواندن با مجوز جاری فیلتر می‌شود؛ تاریخچهٔ دارای snapshot هم مجوز فضای کاری، دپارتمان و مخاطبان خصوصی را دور نمی‌زند. صف یادآور، SMS/ایمیل و اتصال واقعی بیرونی متعلق به مرحلهٔ هفتم‌اند.

`npm run test:stage6` سرویس‌های چت و اعلان، قرارداد رابط، HTTP ساخته‌شده، محتوای صوت/فایل، رسید، rollback، Socket و restart را با دادهٔ جدا آزمون می‌کند. برای اجرای محلی همچنان یک پردازش و دیسک محلی لازم است؛ این مرحله محدودیت مدل سازگاری ذخیره‌سازی در حافظه را به اجرای چندپردازشی تبدیل نمی‌کند.
